# 하루 코스 설계 (v2)

> 상태: 초안 · 작성 2026-10-31 · 이전 MVP: [`mvp-spec.md`](mvp-spec.md)
> 데이터 조사: [`data-sources-research.md`](data-sources-research.md)

## 1. 의도

지금 서비스는 "여행 시간 2 · 4 · 6시간 + 동행 + 관심사"를 받아 **관광지 목록과 총 소요 시간**을 준다. 장소 6곳은 대부분 임시 정보다.

v2의 목표는 **이 사이트의 코스만 보고 청도에서 하루를 보낼 수 있게** 하는 것이다. 몇 시에 어디 도착해서 언제 떠나는지, 점심은 어디서 먹고 어디서 쉬는지, 문 닫은 곳에 보내지 않는지까지 사이트가 책임진다. 이를 위해 장소 데이터를 실제 확인한 정보로 바꾼다.

## 2. 목표 · 비목표 · 반목표

**목표**

- 자가용 당일치기 관광객에게 **시각이 적힌 하루 일정**(관광 · 점심 · 쉬어 가기 · 저녁)을 준다.
- 장소 사이 이동 시간을 **좌표로 계산**한다 (권역 가정 10분/25분 폐기).
- 방문 **요일의 운영시간 · 휴무**를 지킨다. 문 닫은 곳, 마감 뒤 도착하는 곳은 넣지 않는다.
- 장소 데이터를 TourAPI 수집 → 직접 확인 · 작성한 **관광지 25~30곳 + 식당 7~8곳 + 카페 7~8곳**으로 교체한다. 기존 샘플 6곳은 삭제한다.
- 공공누리 제1유형 사진을 상세 · 결과 화면에 출처와 함께 보여 준다.

**비목표 (이번 범위 아님)**

- 기차 · KTX · 대중교통 이동, 숙박 · 1박 이상 일정
- 청도 밖 장소 (오는 길 휴게소 등), 출발지 입력
- 실시간 교통, 지도 SDK(카카오 · 네이버 지도 표시), 길찾기 API
- DB, 로그인, 리뷰, 사진 업로드, LLM
- 공휴일 · 명절 휴무 계산 (요일 규칙만, 예외는 안내 문구로)
- Azure 배포 (구현 완료 후 Terraform으로 따로 진행)

**반목표 (돌아가더라도 실패로 보는 것)**

- 확인하지 않은 운영시간 · 요금을 지어내거나, 휴무일에 그 장소로 보내는 일정
- TourAPI 소개 글을 그대로 옮기거나, TourAPI 응답 원문을 저장소 · 서비스에 넣는 것
- 제3유형 사진을 자르거나 바꿔서 쓰는 것, 출처 표기 없는 사진
- 같은 조건인데 다른 일정이 나오는 것 (비결정적 추천)
- 서비스가 동작 중에 TourAPI를 부르는 것 (외부 장애 · 호출 한도에 서비스가 묶임)

## 3. 제약

- **저장 방식**: DB 없이 JSON 파일 + 시작 시 메모리 로드 유지 ([ADR 0003](../00-overview/decisions/0003-json-instead-of-db.md)). `SpotRepository` 인터페이스 유지.
- **TourAPI 정책**: 한국관광콘텐츠랩 저작권 정책의 "콘텐츠 캐싱(로컬서버 저장방식) 금지" 때문에 TourAPI는 **조사 도구로만** 쓴다. 저장소 · 서비스에 들어가는 것은 우리가 확인한 사실, 우리가 쓴 문장, 우리가 정한 값, 사진 출처 정보다. 수집 원본은 `.data-draft/`(git 제외)에만 둔다. 출처 표기: "데이터 제공: ⓒ한국관광공사".
- **데이터 원칙**: 기존 [`spots-data.md`](spots-data.md) 원칙 유지 — 운영 정보는 확인한 날짜(`checkedAt`)와 함께, 확인 못 한 값은 생략.
- **기존 품질 기준 유지**: 결정적 알고리즘, 모바일 390px, 키보드 · `aria-pressed` · `:focus-visible`, 12px 이상 글자, 44px 터치 영역, 한국어 오류 메시지, 이모지 금지, 토큰 색만.
- **구현 방식**: 코드는 기존처럼 Copilot CLI 루프(프롬프트 → 리뷰 → PR → 머지)로 구현한다. 데이터 확인 · 작성은 Claude가 공식 페이지를 대조해 초안을 만들고, 소유자가 PR에서 확인한다.

## 4. 소유자가 정한 것

| 항목 | 결정 |
|---|---|
| 저장 | DB 없이 JSON 유지 |
| 데이터 방식 | TourAPI로 수집 → 직접 확인 · 작성. 서비스 중 TourAPI 호출 없음 |
| 기존 데이터 | 샘플 6곳 삭제, 수집 데이터 기반으로 새로 작성 |
| 대상 | **자가용** 당일치기 관광객. 기차 · KTX 제외 |
| 범위 | 청도군 안 장소만. 오가는 길 휴게소 등 제외 |
| 식사 | 점심 · 저녁을 일정에 넣는다 |
| 쉬어 가기 | **식사 뒤**에 쉬어 가는 시간(카페)을 넣는다 |
| 저녁 뒤 | 시간이 남으면 **야간 관광**을 이어서 넣는다 (`end` 최대 21:00) |
| 코스 구성 | Claude 판단에 맡김 (아래 5 · 6장) |

## 5. 데이터 설계

### 장소 종류와 규모

| kind | 수 | 출처 | 선정 기준 |
|---|---|---|---|
| `spot` (관광) | 25~30 | TourAPI 관광지 54 · 문화시설 4 · 레포츠 중 체험형(레일바이크, 루지) + 운문사 | 관심사 5종이 고르게, 권역이 고르게, 실내 · 실외 섞이게. 사찰 · 서원은 대표만. 저녁 이후 영업하는 곳(야간 관광용)을 2~3곳 이상 포함 |
| `restaurant` (식당) | 7~8 | TourAPI 음식점 중 식당 14곳 | 청도 대표 메뉴(추어탕, 한재미나리, 한우 등), 권역 분산(특히 운문면 · 화양읍 · 청도읍), 점심 영업 확인 |
| `cafe` (카페) | 7~8 | TourAPI 음식점 중 카페 17곳 | 식당 · 관광지 근처, 권역 분산 |

- **운문사**는 TourAPI 관광지에 없다. 청도 대표 명소라 포함하고, 운문사 · 청도군 공식 페이지로 확인해 작성한다. 사진은 1유형을 못 찾으면 일러스트로 대체한다.
- 캠핑장 · 숙박 · 골프장은 넣지 않는다. 시장(청도시장, 풍각장)은 장날이 있어 이번에는 넣지 않는다.

### Spot 스키마 변경

`Spot` 이름과 `spots.json` 파일은 유지하고 `kind`로 종류를 나눈다 (라우트 · 저장소 변경 최소화).

```ts
export const KINDS = ['spot', 'restaurant', 'cafe'] as const;
export const WEEKDAYS = ['mon', 'tue', 'wed', 'thu', 'fri', 'sat', 'sun'] as const;

export const ZONES = [
  'cheongdo-eup', 'hwayang-eup', 'iseo-myeon', 'gaknam-myeon', 'punggak-myeon',
  'gakbuk-myeon', 'unmun-myeon', 'geumcheon-myeon', 'maejeon-myeon',
] as const; // 청도군 9개 읍 · 면. 표시 · 묶음용 (이동 시간 계산에는 안 씀)

interface TimeRange { open: string; close: string } // "09:30", "18:00" (24시간, 자정 넘김 없음)

interface WeeklyHours {
  days: Record<Weekday, TimeRange[]>; // 빈 배열 = 그 요일 휴무. 쉬는 시간이 있으면 구간 2개
  lastEntryBeforeCloseMinutes?: number; // "마감 15분 전 입장 마감" → 15
  note?: string;                        // 우리 문장. "명절 당일 휴무" 등 요일 규칙 밖 안내
}

interface SpotImage {
  url: string;          // tong.visitkorea.or.kr 원본 주소 (우리 서버에 저장하지 않음)
  alt: string;          // 우리가 쓴 대체 텍스트
  license: 'kogl-1';    // 공공누리 제1유형만 허용
  credit: string;       // "ⓒ한국관광공사" 등 표기 문구
}

interface Spot {
  id: string; kind: Kind; name: string; summary: string; description: string[]; tips: string[];
  zone: Zone;
  location: { lat: number; lng: number };   // WGS84. TourAPI mapy/mapx를 확인 후 기록
  tags: Tag[];          // kind=spot은 1개 이상. 식당 · 카페는 빈 배열 허용
  goodFor: Companion[];
  stayMinutes: number;  // spot 10~240, restaurant 60, cafe 30~40
  meals?: ('lunch' | 'dinner')[]; // restaurant만. 해당 끼니 영업 확인한 것만
  address: string;
  hours: WeeklyHours;   // 필수 — 일정 계산에 쓰므로 확인 안 된 장소는 데이터에 넣지 않는다
  fee?: string; phone?: string;
  images: SpotImage[];  // 0개 이상
  source: string;       // "한국관광공사", "운문사 공식 홈페이지" 등
  sourceRef?: { provider: 'tourapi'; contentId: string }; // 재확인용
  checkedAt: string;    // 필수 — 운영시간을 확인한 날짜
}
```

- 삭제: `routeOrder`(좌표 기반 동선으로 대체), 자유 문자열 `hours` · `closed`(구조화된 `hours`로 대체), `UNVERIFIED_SOURCE`(확인 안 된 장소는 넣지 않음).
- 화면의 "운영시간 · 휴무" 문구는 `hours`에서 만든다 (예: "화~일 09:30–18:00 · 월요일 휴무").
- **"상시 개방" 장소** (수집 초안에서 사찰 · 서원 · 계곡 · 읍성 등 20곳 이상): 그대로 24시간으로 두면 밤 9시에 산사로 보내는 일정이 나온다. `hours`에는 **추천 관람 시간**(기본 09:00–18:00, 해가 진 뒤 볼거리가 있는 곳만 늘림)을 넣고 `note`에 "상시 개방 · 추천 관람 시간 기준"을 적는다. 이 시간은 우리 판단이므로 장소마다 근거를 PR 설명에 남긴다.
- 야간 관광 후보는 실제 야간 영업이 확인된 곳만 쓴다. 수집 초안 기준 청도 프로방스(16:00–22:00), 청도 용암온천 등이다.
- 검증 규칙(zod): 시각 형식, `open < close`, 같은 요일 구간 겹침 없음, `kind=restaurant`면 `meals` 1개 이상, `kind=spot`이면 `tags` 1개 이상, 위경도가 청도군 범위 안(대략 위도 35.5~35.8, 경도 128.5~129.1), id 중복 없음.

### 데이터 작업 흐름

1. **수집 스크립트** (`tools/tourapi/collect.mjs`, 새로 커밋): `.env`의 `TOUR_API_KEY`로 청도군(`lDongRegnCd=47`, `lDongSignguCd=820`) 전체를 목록 · 공통 · 소개 · 이용 · 이미지 순으로 받아 `.data-draft/tourapi-cheongdo.json`에 쓴다. 1회 약 530회 호출. `.data-draft/`는 `.gitignore`에 추가한다.
   - 2026-10-31에 Claude가 일회용 스크립트로 이미 한 번 수집했다 (133건, 533회 호출, 초안은 소유자 PC의 `.data-draft/`에 있음). 커밋할 스크립트는 같은 동작을 Copilot이 저장소 규칙에 맞게 다시 만드는 것이고, 결과 건수(133)가 같은지로 확인한다.
2. **후보표**: 초안에서 종류 · 권역 · 1유형 사진 유무 · 운영시간 원문을 표로 뽑아 선정한다.
3. **확인 · 작성** (장소마다): 공식 홈페이지 · 청도군 문화관광과 운영 정보 대조 → `hours` 구조화 · `checkedAt` → 소개 · 팁을 우리 문장으로 → 1유형 사진 고르기 → 태그 · 동행 · 체류 정하기.
4. `apps/api/data/spots.json`을 새 데이터로 교체하고 PR로 검토한다. 출처가 서로 다르면 PR 설명에 적는다.

## 6. 하루 일정 계산

### 입력 (`/api/course` 쿼리)

| 이름 | 형식 | 규칙 | 화면 기본값 |
|---|---|---|---|
| `date` | `YYYY-MM-DD` | 실제 날짜. 요일은 이 날짜로 계산 (Asia/Seoul) | 오늘 (KST) |
| `start` | `HH:MM` | 30분 단위, 08:00~14:00 | 10:00 |
| `end` | `HH:MM` | 30분 단위, `start` + 3시간 이상, 21:00 이하 | 19:00 |
| `with` | Companion | 기존과 같음 | — |
| `tags` | Tag CSV | 기존과 같음 (1개 이상) | — |
| `exclude` | id CSV | 기존과 같음 | — |

`hours` 파라미터는 없앤다. API는 날짜가 과거여도 받는다 (오늘 기준 검사를 하면 같은 URL이 날짜에 따라 400이 되어 결정성이 깨진다). 화면에서만 과거 날짜를 고르지 못하게 한다.

### 이동 시간

```
거리(km)  = 두 좌표의 하버사인 거리
이동(분)  = ceil5( 거리 × 1.4 ÷ 40 × 60 + 5 )   // 도로 보정 1.4, 평균 40km/h, 주차 · 걷기 5분, 5분 단위 올림
```

- 상수(1.4, 40, 5)는 `packages/shared`의 `TRAVEL` 상수로 둔다. 실제 길찾기 값과 몇 구간 비교해 조정할 수 있다 (조정 시 테스트 기대값 갱신).
- 같은 장소 간은 0분. 응답에 `distanceKm`(소수 1자리)도 담는다.

### 하루 뼈대

```
[오전 관광] → 점심(식당 60분) → 쉬어 가기(카페) → [오후 관광] → (저녁 식당 60분) → [야간 관광] → 끝
```

| 블록 | 넣는 조건 | 시간 창 |
|---|---|---|
| 점심 | `start` ≤ 12:00 이고 `end` ≥ 14:00 (12:00 넘어 출발하면 먹고 온 것으로 보고 넣지 않음) | 식당 **도착** 11:30~13:30 |
| 쉬어 가기 | 점심을 넣었으면 항상, 바로 뒤에 | 점심 직후 |
| 저녁 | `end` ≥ 18:30 | 식당 도착 17:30~19:00 |
| 야간 관광 | 저녁 뒤 `end`까지 시간이 남으면, 그 시각에 영업하는 관광지를 3단계 규칙으로 이어서 넣는다 (예: 청도 프로방스 불빛) | 저녁 직후 ~ `end` |
| 저녁 뒤 쉬어 가기 | 넣지 않음 | — |

### 계산 순서 (결정적)

0. **기다림 허용**: 도착이 영업 시작 · 식사 창 시작보다 이르면 그때까지 기다린다 (`arriveAt` = 늦은 쪽). 기다린 시간은 그 항목의 `waitMinutes`로 담고 `slackMinutes`에 더한다. 화면에서는 이동 행에 "여유 N분"으로 보인다. 첫 장소도 같다 (`start` 08:00, 개장 09:00이면 09:00 도착).
1. **후보 점수**: `kind=spot`만. 점수 = 일치 태그 수 × 10 + 동행 일치 5 (기존과 같음). 일치 태그가 1개 이상인 곳이 **1순위 후보**, 태그는 안 맞고 동행만 맞는 곳(5점)은 **보충 후보**다 — 3단계에서 1순위 후보가 하나도 들어갈 수 없을 때만 쓴다. 0점 · `exclude` · 그 요일 휴무는 뺀다 (휴무는 `excluded`에 `CLOSED_ON_DAY`). `food` 관심사는 관광지(와인터널 등)의 점수에만 쓰고 식당 · 카페 선택에는 쓰지 않는다.
2. **시작 장소 후보**: 점수 상위 5곳 (점수↓ → id↑). 각 시작 장소로 3~5단계를 끝까지 돌려 일정 5개를 만든다.
3. **관광 선택 (탐욕)**: 현재 위치 · 시각에서 남은 후보 중 아래를 모두 만족하는 곳을 고른다.
   - 도착 시각에 영업 중이고, 체류를 마친 시각이 그 구간의 `close` 이하, 도착이 `close − lastEntryBeforeCloseMinutes` 이하
   - 다녀와도 다음 고정 블록(점심 · 저녁 창의 마지막 도착 시각)과 `end`를 지킬 수 있음
   - 이 중 **가치 = 점수 − 0.5 × 이동분**이 가장 큰 곳 (동률: 이동분↑ → id↑)
4. **식사 넣기**: 시각이 식사 창 시작 이상이 되었거나, 다음 관광을 넣으면 식사 창의 마지막 도착 시각을 넘기게 되면 식사를 넣는다. 식당은 해당 끼니(`meals`)에 맞고 도착 시각에 영업 중인 곳 중 **이동분이 가장 짧은 곳** (동률 id↑). 점심 뒤에는 **쉬어 가기**: 영업 중인 카페 중 식당에서 이동분이 가장 짧은 곳. 넣을 곳이 없으면 그 블록을 건너뛰고 `notices`에 남긴다 ("이 시간에 영업하는 식당을 찾지 못했어요").
5. **끝**: 저녁 뒤에도 3단계를 계속 돈다 (야간 관광). 더 넣을 관광이 없거나 `end`를 넘기면 멈춘다. 마지막 블록 종료 ≤ `end`.
6. **5개 일정 중 선택**: 관광 점수 합↑ → 총 이동분↓ → 시작 장소 id↑.
7. `excluded`: 후보였지만 일정에 없는 관광지. 이유 `NOT_ENOUGH_TIME` 또는 `CLOSED_ON_DAY`.

### 응답 (요약)

```ts
interface DayPlanItem {
  order: number;
  type: 'visit' | 'meal' | 'rest';
  meal?: 'lunch' | 'dinner';
  spot: SpotSummary;            // kind · location · 대표 이미지 1장 포함
  travelMinutes: number;        // 이전 항목에서 오는 시간 (첫 항목 0)
  waitMinutes: number;          // 도착 후 영업 · 식사 창 시작까지 기다린 시간 (보통 0)
  distanceKm: number;
  arriveAt: string;             // "10:00"
  leaveAt: string;              // "10:40"
  matchedTags: Tag[]; score: number; // visit만 의미 있음
}
interface DayPlan {
  conditions: DayQuery;         // date, weekday, start, end, with, tags, exclude
  items: DayPlanItem[];
  excluded: { spot: SpotSummary; reason: 'NOT_ENOUGH_TIME' | 'CLOSED_ON_DAY' }[];
  totals: { visitCount: number; stayMinutes: number; travelMinutes: number; startAt: string; endAt: string; slackMinutes: number };
  notices: string[];            // 한국어 안내 문장
}
```

## 7. 화면 변화

- **홈**: 조건 카드 STEP 01이 "여행 시간 2 · 4 · 6"에서 **방문 날짜 + 시작 · 끝 시각**(30분 단위 선택)으로 바뀐다. 나머지(동행, 관심사, 공유 URL 미리보기)는 유지. 장소 카드 6개는 새 데이터의 대표 장소로.
- **코스 결과**: 제목 "11월 7일(토) 가족과 함께하는 청도 하루". 타임라인 카드에 **도착–출발 시각**(10:00–10:40), 종류별 구분(관광 · 점심 · 쉬어 가기 · 저녁, 아이콘 · 배지), 이동 행 "차로 약 12분 · 6.3km". 요약에 일정 시작–끝, 관광 n곳, 이동 합계, 여유 시간, `notices`. 빠진 장소에 휴무 이유 표시. 카드에 1유형 대표 사진(있을 때) + 출처.
- **상세**: 대표 이미지 영역에 1유형 사진(없으면 기존 일러스트), 사진 출처 표기. 운영시간은 요일별 표. "지도에서 보기"는 좌표 기반 링크. 식당 · 카페도 같은 상세 화면을 쓴다(대표 메뉴는 `tips`나 소개에).
- **공통**: 푸터 "데이터 제공: ⓒ한국관광공사" 추가. 상태 화면(로딩 · 빈 결과 · 400 · 404) 문구를 새 입력에 맞게 수정.

## 8. 성공 기준

- 고정 데이터(테스트 픽스처)로 만든 일정이 손으로 계산한 기대값과 같다: 시작 장소 선택, 개장 전 기다림, 점심 창 · 쉬어 가기 삽입, 12:00 넘은 출발의 점심 생략, 저녁 조건, 저녁 뒤 야간 관광, 월요일 휴무 제외, 입장 마감, 보충 후보 사용, 식당 없음 안내.
- 실제 데이터로 대표 조건 3개(토요일 10:00–19:00 가족 자연 · 체험 / 월요일 커플 사진 · 먹거리 / 평일 09:00–14:00 혼자 역사)의 일정이 사람이 봐도 무리 없다 (휴무지 없음, 점심 11:30~13:30 도착, 운문면 왕복 같은 긴 이동이 불필요하게 없음). 리뷰 기록에 남긴다.
- 모든 장소에 `hours` · `checkedAt` · 좌표가 있고, 사진은 전부 `kogl-1` + 출처.
- 기존 품질 검사(타입 · 린트 · 테스트 · 포맷), 390px · 키보드 접근성, Docker 리허설 통과.

## 9. 진행 순서 (계획 단계에서 구체화)

## 10. 조정 규칙

실제 데이터 일정 검토(8장)에서 무리한 일정이 나오면, 먼저 데이터(체류 시간, 포함 장소)를 고친다. 그래도 안 되면 상수(`TRAVEL`, 이동 가중치 0.5, 시작 후보 수 5)를 조정할 수 있다. 바꾼 값과 이유는 리뷰 기록에 남기고 테스트 기대값을 갱신한다. 탐욕 선택 · 블록 순서 같은 규칙 자체를 바꾸려면 소유자 확인을 받는다.
